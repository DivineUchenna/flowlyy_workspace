# Upwork Cover Letter (fast path)

The lighter sibling of `upwork-application`. Same cover letter shape, same hard
rules, same "never invent results" discipline — it just skips the parts of that
skill that exist to produce a demo: no template search/build, no pause for a Loom
recording. Use it when a demo isn't the right investment for this job, not as a
default shortcut — `upwork-application`'s demo-backed proposals convert better, so
route there first unless Divine has actually said to skip it.

## Trigger

Divine pastes a job post *and* signals he wants to skip the demo step — either
explicitly ("just the cover letter," "skip the demo") or because the job is
small/fast enough that building a template would be overkill for the size of the
ask. If it's ambiguous, ask rather than assuming — going straight to a no-demo
cover letter on a job that actually warranted a demo is a real cost, not a
free shortcut.

## Step 1 — Name the sharpest pain point

Same method as `upwork-application`: read the job description only, name **one**
pain point — the sharpest, most specific, most costly one — in a single sentence.
Everything else anchors to it.

## Step 2 — Find the proof, without building anything new

No template gets built in this path. The proof stack has to come from what's
already real:

- **Divine's existing work** — his own automations (e.g. the LinkedIn outreach
  system), a Flowlyy product, other verified prior work that's a genuine, even if
  partial, match to this job. Say plainly that it's existing work, not something
  built for this application — same honesty rule as `upwork-application`.
- **A genuine expertise signal** — a real risk worth flagging before the client
  hits it, a design decision most builders in this space get wrong, a specific
  technical judgment call. This only counts if it's actually true and specific to
  this job; a generic "I pay attention to detail" isn't a signal, it's filler.

**If neither exists** — no relevant prior work and no genuine differentiator to
name — stop and say so. Don't manufacture a proof stack from nothing; that's
exactly the failure mode this skill exists to avoid. Tell Divine the honest
options are: apply without a strong proof stack (weaker but sometimes still
worth sending), or switch to `upwork-application` and actually build a demo for
this one.

## Step 3 — Draft the cover letter

Same structure as `upwork-application`'s cover letter (kept in sync
intentionally — if that structure changes, this should too):

1. **Personalized open** — one line, state the specialism directly. Never "I am
   a...".
2. **Bridge line** — one sentence tying to the specific technical problem in
   *this* job, not a generic pitch.
3. **Proof stack (✔️, 3-5 items, one line each)** — the existing-work reference
   and/or genuine expertise signal from Step 2. Never a client-results list,
   never a claim that anything is already live in their system.
4. **Scope-as-checklist (✅)** — concrete deliverables, always a list, never a
   single sentence.
5. **Numbered next steps** — "1. Send a message on Upwork, 2. <specific thing to
   confirm>", never a vague "let's chat."
6. **Sign-off** — first name only.
7. **PS** — one genuine differentiator or an honest scope caveat, never filler.

## Screening-question answer bank

Beyond the three core questions `upwork-application` covers (why you're a fit,
describe a similar project, how you'd approach this), also handle these when the
job post asks — short, structured, specific to *this* job, never a template
answer reused across applications:

- **Tone/voice questions** ("how do you decide what tone to use," "how would you
  match our brand voice") — answer with the actual factor that drives it (the
  objective of the piece, who's reading it), not a generic "I adapt to the
  client."
- **How you use data/metrics to inform decisions** — name the specific metric
  that actually matters for *this* kind of build (e.g. for an outreach agent:
  acceptance rate and false-positive rate on approval gates, not a generic
  "I track KPIs").
- **How you handle a difficult client conversation** — one honest, specific
  approach (e.g. "I flag scope risk before it's a problem, not after"), not
  therapy-speak.
- **What makes you different from other freelancers in this category** — only
  answer this if there's a real, specific differentiator; if not, skip the
  device entirely rather than forcing one.
- **"How would you approach a project like X"** — a short numbered process
  specific to the pain point from Step 1, same as `upwork-application`'s
  version of this question.

## Hard rules

- **No template/demo gets built in this path.** If the job genuinely needs one to
  compete, that's a signal to switch to `upwork-application`, not a reason to
  fake one here.
- **Never invent results, clients, metrics, or existing-build claims.** If Step 2
  finds nothing real, say so — see Step 2.
- **Never claim a build is live or already running for the client.**
- **Never copy phrasing, structure filler, or claims from any reference
  proposal.** Structure only, fresh words every time.
- **Plain English.** No "passionate," "results-driven," "leverage," "seamless."
- **General niche, not forced-construction** — this serves any industry's
  automation job, same as `upwork-application`.

## Output format

```
## Pain point
<one sentence>

## Proof stack source
<existing build referenced, and/or the genuine differentiator — or a plain
statement that neither exists and Divine should decide how to proceed>

## Cover letter
<full proposal text>

## Screening-question answers
<only if the job post includes them>
```
